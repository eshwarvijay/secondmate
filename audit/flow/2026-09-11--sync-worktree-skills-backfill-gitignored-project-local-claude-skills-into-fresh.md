## 2026-09-11 — sync-worktree-skills: backfill gitignored project-local .claude/skills/ into fresh worktrees

- **Trigger:** a live, real-world bug report mid-session — the human hit `Error: Unknown skill: agent-analytics/.claude/skills/emil-design-eng` while using secondmate's worktree pattern inside a totally different repo (`archie`). Root-caused directly by the supervisor before any task was scoped: `agent-analytics/.claude/skills/emil-design-eng` genuinely exists (27KB, real content) in `archie`'s primary checkout, is untracked (`**/.claude/skills/` is gitignored there), and `git worktree add` — used both by `bin/new-worktree.sh`'s headless fallback and by the external `herdr worktree create` tool secondmate doesn't own — only ever populates a worktree from committed content, so the skill was genuinely absent from an already-created sibling worktree of the same repo. An earlier hypothesis (a Claude Code CLI-level "SKILL ACTIVATION CHECK" suggestion-hook mismatch, investigated and confirmed real but genuinely out of scope — no file anywhere backs those suggested skill names) was explicitly ruled out as unrelated once the concrete error message arrived.
- **Human scope decisions (two rounds of `AskUserQuestion`):** (1) fix approach — copy (never symlink) missing `.claude/skills/` directories into a fresh worktree, specifically because a symlink pointing back outside the worktree would be resolved and denied by `bin/scope-guard.py`'s own existing path-confinement check, a real conflict with an existing security control; (2) scope — narrowly `.claude/skills/` only, explicitly declining to sync other gitignored `.claude/*` paths (settings.json/settings.local.json — possibly sensitive local config; compaction_log.txt/task_state.md/session_handoff.md/loop_*_state.md — session-specific state that would be actively wrong to duplicate into a fresh worktree, not just unhelpful) after the supervisor laid out exactly what else that repo's own `.gitignore` contained.
- **Maker path:** pi + Claude Sonnet 5 (`global.anthropic.claude-sonnet-5`, high thinking), dedicated worktree workspace `w2E`, root pane `w2E:p1` — routed to Sonnet-5 given the genuine security-relevant reasoning involved (copy-vs-symlink, scope-guard interaction) rather than a purely mechanical fix.
- **Worktree:** `herdr worktree create` → `sm/sync-worktree-skills`.
- **Rounds:** 4 real fix rounds across 3 real checker rounds (`gpt`), each round's finding independently reproduced by the supervisor — including, critically, testing against the ACTUAL real `archie` repo and worktree that started this whole investigation, not just synthetic fixtures:
  1. **(supervisor-found, before any checker round):** round 1 shipped a straightforward "copy any missing `.claude/skills/<name>` plain directory" implementation, whose own synthetic selfcheck fixture passed cleanly — but running it against the REAL archie case did NOTHING: the real skill entry is itself a SYMLINK (`.claude/skills/emil-design-eng -> ../../.agents/skills/emil-design-eng`), and the enumeration filtered strictly on `-type d` (lstat semantics, excludes symlinks), silently skipping the exact case that motivated the task while still exiting 0. Fixed by resolving symlinked skill entries via `python3 os.path.realpath` (chosen for GNU/BSD portability, matching an existing precedent in `bin/scope-guard.py`) and materializing the REAL resolved content as a genuine directory in the worktree — never as a symlink, since the resolved target (`.agents/skills/`) was itself ALSO gitignored and ALSO missing from the worktree, so preserving the symlink would have just created a dangling link. Re-verified directly against the real archie repo: byte-identical content, correct path.
  2. **(checker round 1, most severe):** a symlink resolving to anywhere OUTSIDE the primary checkout (e.g. an absolute path like `/tmp/external-secret`) was silently followed and its content materialized into every new worktree — a real security-relevant leak. Independently reproduced by the supervisor with a fixture symlink to sensitive external content before routing. Fixed with a boundary check against the canonicalized `--primary` root; anything resolving outside it is skipped with a clear warning, treated the same as a dangling symlink.
  3. **(checker round 1, same round):** `bin/new-worktree.sh --selfcheck`'s own EXISTING test suite had zero coverage for the new wiring call — neutralizing that one line to a no-op still passed. Independently confirmed by the supervisor via the identical mutation before routing. Fixed with a real fixture-based assertion using the actual `new-worktree.sh` code path, not a mock.
  4. **(checker round 2):** the existence guard `[ -e "$target" ]` follows symlinks, so a DANGLING symlink already sitting at a target path (e.g. a previously tracked symlink, later superseded in primary by a real gitignored directory of the same name) was not recognized as "already present" — the script proceeded to `mv` a real directory onto it, which failed with `mv: ... Not a directory`. Since `bin/new-worktree.sh` runs under `set -euo pipefail`, this would abort the ENTIRE worktree-creation call, not just skip one sync step — independently reproduced by the supervisor with the exact scenario before routing, confirming the identical failure. Fixed by widening the guard to `[ -e "$target" ] || [ -L "$target" ]` (lstat semantics, detects the symlink's own existence regardless of whether it resolves to anything).
  5. **Checker round 3: clean pass, zero findings**, after independently re-running every prior round's mutation test itself and auditing the file for any OTHER instance of the same "`-e` without `-L`" bug class (found none — the only target-presence guard in the file already had the fix; other `-d` checks are unrelated input/resolved-directory validation). One spec ambiguity noted but explicitly not treated as a defect: a tracked dangling symlink at an ANCESTOR directory (not the target itself) blocking `mkdir -p` of a missing target's parent — the documented non-overwrite contract covers an existing target entry, not an existing ancestor path, so this narrower edge case was left as a named, accepted gap rather than chased further.
- **Supervisor verification discipline:** every fix in this task was validated against BOTH a synthetic fixture AND the real archie repo/worktree that originally surfaced the bug — the real-world check caught round 1's complete failure that the synthetic fixture alone would never have revealed, since the synthetic fixture never modeled a symlinked skill entry.
- **Missed convention (self-caught, twice in a row now):** the supervisor again forgot this repo's own version-bump convention on the initial merge — main sat at `0.1.18` with a new commit and no bump, a repeat of the identical gap caught and fixed after the `dispatch-loop` task earlier this same session. Fixed directly (`0.1.18` → `0.1.19`) along with the README "What's inside"/selfcheck-chain entries for the new script, which the merge had also not included.
- **Outcome:** verify-gate PASS at `9f6504b` (checked-sha match) → human hold `b454cb3c` answered `merge` (genuine per-task `AskUserQuestion`) → merged to main via `bin/merge-sequencer.sh` (its fourth real production use) at `e7cd88a` → version bump + README sync fixed and pushed separately at `cde10d1` → full repo-wide selfcheck chain re-run clean (`ALL_OK`) on the actual final state → `claude plugin validate .` passed → worktree/branch/workspace/marker torn down.
- **Lesson:** this task is the clearest demonstration yet in this repo's history that a synthetic selfcheck fixture, however careful, is not a substitute for testing against the actual real-world case that motivated a fix — round 1's fixture was well-constructed and passed cleanly, but it modeled the WRONG shape of the problem (a plain gitignored directory) and would have shipped a fix that did literally nothing for the real bug report. The supervisor's decision to keep the real archie repo/worktree available as a live validation target throughout the task, rather than relying solely on the worktree's own increasingly elaborate synthetic fixtures, is the specific practice that caught this — worth repeating whenever a task originates from a concrete, reproducible real-world report rather than a hypothetical.
