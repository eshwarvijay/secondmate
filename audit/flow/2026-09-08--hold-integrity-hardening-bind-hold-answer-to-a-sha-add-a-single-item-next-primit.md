## 2026-09-08 — hold-integrity-hardening: bind hold/answer to a SHA, add a single-item "next" primitive

- **Trigger:** architecture research for a planned multi-task-dispatcher feature surfaced two real integrity gaps in `bin/hold.py`: no binding between a hold/answer and the commit SHA it applies to (an answer could be silently reattached to a later, different code state), and no single-item serialization primitive for processing concurrently-open holds one at a time.
- **Maker path:** pi + Claude Sonnet 5 (`global.anthropic.claude-sonnet-5`, high thinking) via `herdr agent start --pane <root_pane_id>`, dedicated worktree workspace `w1V`. First real use of Claude Sonnet 5 as a pi-driven maker in this repo — required discovering the correct model id (`global.anthropic.claude-sonnet-5`, not the bare `anthropic.claude-sonnet-5`, which fails with an inference-profile error) after one failed restart.
- **Worktree:** `herdr worktree create` → `sm/hold-integrity-hardening`.
- **Checker:** `global.openai.gpt-5.6-terra` (genuine cross-vendor maker≠checker pair), lenses `redteam/access-control`, `qa/test-reality`, `qa/coverage`.
- **Rounds:** 1 checker round, clean PASS with zero findings — but only after discovering and working around a real infrastructure bug (see below) that caused the checker's FIRST invocation to spuriously refuse.
- **Infrastructure bug discovered and fixed mid-task (not a hold.py bug):** `herdr pane run <pane> bash -lc "cd '<dir>' && cmd1 && cmd2; echo MARKER"`, when invoked through the Bash tool, silently mis-splits — the outer shell's `"..."` quoting is consumed locally and never reaches the pane's terminal as one token; `herdr pane run` reconstructs a bare, unquoted line, so `-lc`'s argument becomes just `cd` (running a no-op subshell `cd` to `$HOME`) and everything after the first `&&` executes in the *pane's own persistent shell cwd* instead of the intended worktree. This silently broke the checker recipe for BOTH the plan-committee-fix round-2 and hold-hardening round-1 checker launches: both ran against the *primary checkout* (still at the pre-task base commit) instead of the worktree, and both correctly (from their own vantage point) refused with "the stated changed revision is not present." Confirmed via a direct minimal probe (`pwd`/`git rev-parse HEAD` printed the primary checkout, not the worktree) and fixed by writing the full multi-command checker invocation to a real script file on disk and calling `herdr pane run <pane> bash /path/to/script.sh` (a single argv token, nothing for the argv-to-PTY-line reconstruction to corrupt) — both checkers were relaunched this way and produced real reviews against the real diffs.
- **Supervisor verification discipline:** independently read the full diff, ran `bin/hold.py selfcheck` directly, and personally mutation-tested both new guards before trusting them — neutered the sha-mismatch check (confirmed the selfcheck's `mismatched --sha on answer must fail` assertion then genuinely raised), and flipped `_oldest_open`'s `min` to `max` (confirmed the `next must return the single oldest open hold` assertion then genuinely failed) — both restored and reconfirmed clean afterward.
- **Outcome:** verify-gate PASS at `519be2d` (checked-sha match) → human hold answered `merge` (genuine per-task AskUserQuestion) → merged to main `--no-ff` at `262db0f`, clean, no conflicts → full repo-wide selfcheck chain re-run clean (`ALL_OK`) on the actual merged commit → pushed → worktree/branch/pane torn down.
- **Lesson:** the `herdr pane run` quoting bug above had been silently present in every prior task's "split a pane off the worktree's root pane, run the checker there" recipe (introduced in the `checker-progress` task) — it happened to go undetected before now because the checker's own refusal ("wrong SHA, diff absent") looks superficially like a legitimate defect report rather than an infrastructure failure, and no prior task's supervisor cross-checked the pane's actual `git rev-parse HEAD` against the worktree's real HEAD before trusting a refusal. Any future `herdr pane run` invocation carrying more than one shell token must go through a script file, never an inline `bash -lc "multi; command; string"`.
