  1. **(round 1):** `cmd_tag`'s (the new `lesson-lookup.py tag` subcommand) read-frontmatter/increment/atomic-write cycle had no lock at all — 20 real concurrent `tag` subprocesses against the same lesson file lost most of their increments (`helpful_count` landed at 8, not 20), a genuine risk now that a few sub-supervisors can run concurrently and reach their own task-close tagging step around the same time. Same round: `_LESSON_ID_RE` validated each `/`-segment's charset but had no length bound at all (a 129-char segment was accepted and written) — fixed with claim-ledger.py's own 1-128-char-per-segment precedent.
  2. **(round 2):** the round-1 per-segment length fix didn't close the whole gap — 40 individually-valid 128-char segments joined into a path long enough that the OS itself raised an unhandled `OSError: File name too long`, crashing `cmd_tag` with a traceback instead of a clean rejection.   3. **(round 3):** `_check_herdr` (the new `bin/teardown-check.sh`) conflated "the herdr call itself failed for an unrelated reason" (daemon unavailable, any other nonzero exit) with "the agent genuinely doesn't exist," silently reporting `[herdr] clean` for a transient herdr-daemon failure. The exact same bug class this repo's own `merge-sequencer.sh` (task `git-coordinator`, same day) had already hit and fixed by eliminating the pipe entirely rather than narrowing the race window.
  4. **(round 4 fix, round 5 finding):** the round-3 pipe-elimination fix (`out="$(...)" || true`) closed the SIGPIPE race but silently swallowed a GENUINE producer failure (e.g. `git worktree list --porcelain` exiting 128 for an unrelated reason) — treating it identically to "producer succeeded, no match," i.e. still a false `clean`. Generalized the fix the same way `_herdr_agent_state` already distinguishes present/absent/unknown: both `_check_worktree` and `_check_claim` now capture the producer's exit status separately and report `unknown` on a genuine failure, never `clean`.
  5. **(round 6):** `_check_worktree`'s post-fix `case "$out" in *"branch refs/heads/sm/$2"*)` was a bare substring match, not an exact-branch match — porcelain's branch line for an unrelated branch like `sm/foo-bar` literally CONTAINS `branch refs/heads/sm/foo` as its own prefix, so task-id `foo` falsely matched `foo-bar`'s worktree.
