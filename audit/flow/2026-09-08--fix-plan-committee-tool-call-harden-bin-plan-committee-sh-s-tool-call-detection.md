## 2026-09-08 — fix-plan-committee-tool-call: harden bin/plan-committee.sh's tool-call detection and output-directory collision guard

- **Trigger:** real, reproduced bug from earlier this session — two of six headless `pi` planner calls (kimi-k2, qwen3-coder) intermittently emitted literal tool-call-formatted text instead of prose, silently accepted as valid output; plus a separate real bug where re-running the committee without a fresh `--out-dir` silently clobbered a previous task's still-relevant planning output.
- **Maker path:** `global.openai.gpt-5.6-terra` as BOTH maker and checker — a deliberate, user-approved, disclosed exception to the maker≠checker invariant for this one task only (the user explicitly confirmed "Yes, really use gpt-5.6-terra for both" after the supervisor flagged the conflict). - **Infrastructure bug discovered and fixed mid-task (not a plan-committee.sh bug, documented in full in the `hold-integrity-hardening` entry above since both tasks hit it the same day):** the standing "split a pane off the worktree's root pane, `herdr pane run` the checker" recipe silently mis-splits an inline `bash -lc "cd '<dir>' && cmd1 && cmd2"` string passed through the Bash tool — the outer shell's quoting doesn't survive `herdr pane run`'s argv-to-PTY-line reconstruction, so `-lc`'s argument collapses to just `cd` (a no-op) and everything after runs unguarded in the pane's own persistent shell cwd (the primary checkout, not the worktree). This caused checker round 2 here (and round 1 of the concurrently-running `hold-integrity-hardening` task) to spuriously "refuse" with a plausible-looking-but-false "stated changed revision is not present" diagnostic. Fixed for the rest of this task (and every checker round after) by writing each round's full checker invocation to a real script file on disk and calling `herdr pane run <pane> bash /path/to/script.sh` (a single argv token, nothing for the reconstruction step to corrupt).
- **Rounds:** an unusually long task — 13 checker rounds, 14 real fix commits, every single round finding and fixing a genuine, independently-reproduced bug (a rare run where literally every round mattered; no wasted/fake-finding rounds). In order:
  1. **(pre-existing from before this task)** TOCTOU race in the output-directory task-marker check-then-write sequence → atomic `mkdir`-based lock.
  2. **(pre-existing)** no regression coverage for independent simultaneous dual-model retry-budget isolation → `FAKE_DUAL_BAD` fixture added.
  3. `committee-output.py`'s `extract()` crashed with an unhandled `TypeError` on a structurally-plausible-but-malformed `{"messages": null}` event (key present, value `None` — the `.get(..., [])` default only applies when the key is absent) — no output file written, unhandled traceback dumped to stderr on every occurrence.
  4. `_run_planner`'s `run-round.sh` invocation discarded its own process exit code entirely via `|| true` — a stub `pi` that emitted perfectly valid JSON prose and then exited 17 caused the ENTIRE six-planner committee to report full success, even though `audit.jsonl` correctly recorded the nonzero exit the whole time.
  5. Fixing #4 exposed a new gap: even with the aggregate exit code now correctly nonzero, a FAILED planner's own `.md` file was left holding the retry's leftover (structurally valid, therefore misleadingly readable) text, and the summary table still printed `+` (clean) for it — exactly the file the supervisor's own downstream synthesis step reads and trusts. Fixed with `rm -f "$out"` on the final failure path.
  6. `BAD_TOKENS`' exact-substring matching (`"<tool_call>"`, `"<|tool_calls_section_begin|>"`, `"<function="`) was bypassed by a trivial whitespace variant of the identical known dialect (`"<tool_call > <function =read_file>"`).
  7. Fixing #6 with one more literal (`tool_call_begin`) started a genuine whack-a-mole: round 8 found `tool_call_argument_begin` also undetected, a THIRD distinct sub-token of the same Kimi `<|tool_call...|>` family slipping through one at a time. Round 9 stopped enumerating and generalized to one structural regex (`<\s*\|\s*tool_call[a-z_]*\s*\|\s*>`) matching the whole family by shape — independently confirmed to catch two sub-tokens (`tool_call_end`, `tool_calls_section_end`) that were never individually coded anywhere, proving it was a real generalization and not another point-patch.
  8. The task-marker collision guard's `find` only checked non-empty `*.md` — missed `*.md.raw` (a directory retaining only a prior failed planner's raw diagnostic was silently claimable by a different task, destroying the evidence), then `audit.jsonl` (the shared audit trail, same gap), then a zero-byte `.raw` (excluded by `-size +0c`), then a symlink (excluded by `-type f`), then a directory entry (excluded by both `-type f` and `-type l`, crashing `committee-output.py` with `IsADirectoryError` after the marker was already written and 5 other planners had already run) — each fixed by widening rather than special-casing, culminating in dropping the `-type` restriction entirely (existence alone, any entry type, refuses).
  9. The generalized Kimi regex's character class (`[a-z_]*`) itself proved too narrow — a digit suffix (`tool_call2`) bypassed it; widened to `[a-zA-Z0-9_]*`.
  10. `find "$out_dir" -maxdepth 1 ...` includes the starting path itself at depth 0 — an out-dir whose OWN basename happened to match a protected pattern (e.g. `--out-dir /tmp/release-plan.md`) was falsely refused as if already containing protected content. Fixed with `-mindepth 1`.
  11. **The most severe finding of the task:** `find ... | grep -q .` can fail OPEN under a SIGPIPE/`pipefail` race — `grep -q .` exits immediately on its first match, closing its stdin; if `find` is still writing more matches at that instant (realistic with a large number of matching entries, reproduced deterministically with 30,000 filler files), `find` is killed by SIGPIPE (exit 141), and under `pipefail` this nonzero pipeline status is treated as "no match found," silently skipping the refusal exactly when it should fire — the checker's own repro showed a real `PRIOR EVIDENCE` file getting silently overwritten. Fixed by replacing the pipe entirely with `[ -n "$(find ... -print -quit)" ]` (no pipe, no grep, `-quit` stops at the first match) — structurally eliminating the race rather than narrowing its window.
  12. A sibling of #11's failure class, different root cause: a `find` that fails outright (e.g. the out-dir chmod'd to `0300`, unreadable, "Permission denied") produces empty stdout exactly like a genuinely-empty successful search — the code only ever checked stdout emptiness, never `find`'s own exit status. Fixed by capturing both (extracted into a named `_unmarked_output_dir_is_safe()` helper returning a 3-way 0/1/2 result), failing CLOSED on inspection failure with a distinct "refusing to inspect" message.
  13. **Clean pass.** Explicit "ready to ship" recommendation from the checker after a full fresh pass across the entire accumulated diff found nothing new.

- **Lesson:** this task is the clearest example yet in this repo's history of "generalize, don't enumerate" paying off across multiple, unrelated dimensions of the same file — the Kimi tool-call detection went through 3 rounds of literal-token whack-a-mole before generalizing to a structural regex, and the collision guard went through 6 rounds of type/size/entry-kind whack-a-mole before generalizing to "existence alone, any type, fail closed on any inspection uncertainty." Both times, the generalization was not just correct but SIMPLER than the enumeration it replaced (fewer characters in the regex; fewer clauses in the find expression) — a strong signal that the enumeration was the wrong abstraction from round 1, not a reasonable starting point that needed patching. The other reusable lesson: a fail-open bug hiding inside a security/integrity-relevant guard (the SIGPIPE race, the permission-denied case) is categorically worse than a missed edge case, because the guard's own FAILURE MODE silently disables the exact protection it exists to provide — worth explicitly asking a checker to hunt for sibling instances of the same failure class elsewhere in the diff once one is found (asked and confirmed clean in round 12 here).
