## 2026-09-11 — doctor-heal-stale-report: bin/doctor.sh's --heal command shows the pre-heal state in its own trailing table

- **Trigger:** discovered live, mid-session, while actually using `doctor.sh --heal` to install the just-merged dispatcher primitives into this running Claude Code session (the user asked to "install the new plugin"). The marketplace checkout at `~/.claude/plugins/marketplaces/secondmate` had itself gone stale (never `git pull`ed for several tasks), which the supervisor first diagnosed and fixed directly (a plain `git pull --ff-only` in that checkout, not requiring a maker task). Only once the marketplace checkout was current did `doctor.sh --heal --yes` correctly classify the install as genuinely `stale` (not the misleading `reload_pending` it had shown before the pull) and successfully heal it — but that SAME invocation's own trailing status table still printed `[!!] secondmate plugin (stale)` even though the heal had provably succeeded (SHA/version verified advanced in `installed_plugins.json`). A separate, fresh `doctor.sh` invocation run immediately after correctly showed `[ok]`.
- **Root cause, confirmed by direct code reading before any maker was involved:** `detect()` runs ONCE at the top of the script (before the final `case` statement), populating the global `ROWS` string and 5 counters via `add()`. The `--heal` branch calls `heal()` (which genuinely mutates real on-disk state) and then `emit_table()` — but `emit_table()` only ever prints the PRE-heal `ROWS`/counters from the original top-of-script `detect()` call; nothing re-runs detection after `heal()` actually changes things.
- **Planning:** adhd skipped (mechanical, closed-ended, known root cause — matches the global CLAUDE.md gate). 6-model plan-committee run per this repo's unconditional-committee convention. Noise discarded during synthesis: one planner's extensive OS-command-injection/unbounded-JSON-parsing/secrets-in-logs security section (inapplicable — this task never touches `heal()`'s or any `_detect_*` function's actual git/JSON-handling code, only the ordering of when they're invoked relative to `emit_table`); concerns about concurrent-process counter corruption (bash globals aren't shared across processes, only within one).
- **Maker path:** pi (Qwen3-Coder-Next, medium thinking), dedicated worktree workspace `w24`, root pane `w24:p1`.
- **Worktree:** `herdr worktree create` → `sm/doctor-heal-stale-report`.
- **Rounds:** 2 real checker rounds (`gpt`), each real:
  1. **(checker round 1):** the fix correctly touched BOTH `--heal` branches (with and without `--yes`), but the new regression test (Test M) only exercised the `--yes` path — the interactive branch's fix was real but had zero coverage confirming it worked. Fixed with a new Test N reusing the same fixture, piping the real confirmation input (`y\n`, matching `_heal_secondmate`'s actual `read -r ans` / `y|Y` check) via stdin.
  2. **Checker round 2: clean pass, zero findings**, after independently re-deriving the isolated-mutation proof that Test N genuinely exercises the interactive path (not vacuously redundant with Test M) and confirming Test N's piped input actually matches the real prompt's expected format.
- **Supervisor verification discipline:** mutation-tested the fix twice, independently, before ever routing anything to the maker or trusting the checker: (1) reverted BOTH `_reset_detect_state; detect` insertions in a scratch copy within the worktree (a copy outside the worktree broke on an unrelated path-resolution assumption, corrected mid-attempt), confirmed the selfcheck's Test M then failed with the exact predicted symptom (captured subprocess output showing `[!!] secondmate plugin (stale)` despite a successful heal); (2) after round 1's fix, did an ISOLATED mutation reverting ONLY the non-`--yes` branch's insertion (leaving `--yes` fixed), confirming Test M still passed while Test N specifically failed — proving Test N was a real, independent regression guard and not redundant coverage. Also independently confirmed `emit_json()` is byte-identical to main before and after (the `--json` path never calls `heal()`, so it should never be touched, and wasn't).
- **Discovered but explicitly deferred (not fixed, not in scope):** (1) a structural limitation in this exact selfcheck fixture family — `_detect_secondmate_status`'s `running_version` reads from the REAL executing script's own `.claude-plugin/plugin.json` with no env-var override, so a synthetic fixture using fake version strings can only ever reach a `reload_pending` post-heal state, never a genuine `ok` state; the test's assertion ("not stale") is the correct, achievable contract given this constraint, not a weaker stand-in that should be strengthened; (2) a separate, pre-existing bug (predates this task, not introduced or touched by it): `emit_table`'s bottom `STATUS:` summary line says "needs healing (doctor.sh --heal)" identically for BOTH a genuinely `stale` row and a `reload_pending` row, because `_detect_secondmate_staleness` tags both via the same `add STALE ...` call sharing one `stale_count` bucket — misleading for `reload_pending`, whose real remedy is `/reload-plugins`, not more healing. Confirmed real via direct testing in this same live session (the very first `doctor.sh` run of this task showed exactly this), flagged to the human, left for a separate future task.

- **Lesson:** this is the first bug in this repo's history discovered through genuine, incidental USE of a tool (installing the plugin for a real reason) rather than through a dedicated audit/checker pass — worth remembering that routine operational use of this repo's own tooling is itself a legitimate discovery channel, not just a formal review process. Also: the marketplace-checkout-never-pulled precondition (fixed ad hoc before the actual bug task even started) is itself a reminder that `doctor.sh`'s own staleness detection assumes the marketplace checkout is kept reasonably fresh by something else — a gap worth remembering if this class of "both sides are stale, so they trivially agree" false-negative resurfaces elsewhere.
