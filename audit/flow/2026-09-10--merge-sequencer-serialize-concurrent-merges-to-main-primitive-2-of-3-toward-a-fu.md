## 2026-09-10 — merge-sequencer: serialize concurrent merges to main, primitive 2 of 3 toward a future multi-supervisor dispatch loop

- **Trigger:** built in parallel with the sibling `claim-ledger` task, both from the same "build all these with each as a task" instruction, same plan-committee synthesis session (see `claim-ledger`'s own flow.md entry for the shared adhd/6-model committee background).
- **The key structural insight that shaped the whole design:** the supervisor read `bin/verify-gate.sh`'s actual code before writing the plan and found its `--base` resolution is a plain `git rev-parse --verify` executed at call time — already fresh for this repo's real topology (one local `.git` shared by the primary checkout and every worktree via `git worktree`). An independent adhd ideation pass converged on the identical point unprompted: "the actual missing primitive isn't a lock at all, it's making sure verify-gate.sh gets re-invoked fresh, atomically, right before the merge" — the lock's job is efficiency/ordering, not correctness. This meant no new flag on verify-gate.sh was ever needed, and the whole task stayed scoped to wrapping it rather than duplicating its checks.
- **Maker path:** pi + Claude Sonnet 5 (`global.anthropic.claude-sonnet-5`, high thinking), dedicated worktree workspace `w10`, root pane `w10:p1`, run in parallel with `claim-ledger` the entire way through — including the same supervisor process gap (see `claim-ledger`'s entry: rounds 1-2 were supervisor-self-reviewed, corrected to a genuine `gpt` checker from round 3 onward after the user caught it).
- **Rounds:** an unusually long task even by this repo's own standards — 7 real checker rounds, 7 real fix commits, every single round finding a genuine, independently-reproduced bug:
  1. **(checker round 1):** `--branch` was never validated against `--worktree`/`--checked-sha` at all — verify-gate.sh only confirms the WORKTREE's own HEAD matches `--checked-sha`; the script then merged WHATEVER `--branch` string was passed, with zero check that it was the same reviewed commit. Reproduced directly: a reviewed `good` worktree/SHA paired with a completely separate, never-reviewed `evil` branch — `evil`'s content merged and pushed, `good`'s never did. Fixed with a `BRANCH_MISMATCH` reason code requiring `--branch`'s own resolved commit to equal `--checked-sha` exactly. Same round: `git merge --abort` was called unconditionally on ANY merge failure, including one caused by a PRE-EXISTING, unrelated in-progress conflict on `$repo` that this invocation never started (a human's own unresolved conflict resolution) — destroying state that was never this script's to touch. Fixed by checking for an existing `MERGE_HEAD`/dirty state BEFORE ever attempting the merge, refusing (exit 2) without ever calling `--abort` in that case.
  2. **(checker round 2):** the lock and ledger both defaulted to paths relative to the CALLING PROCESS's ambient CWD, not to `--repo` — since every herdr-launched sub-agent runs with its CWD set to its own worktree, two siblings targeting the same `--repo` from their own different worktrees would resolve to two entirely different locks/ledgers and never actually serialize. Reproduced directly: a pre-existing lock at `<repo>/.secondmate` completely ignored by an invocation run from a sibling worktree, which merged and pushed straight through. Fixed by anchoring both defaults to `$repo`, computed after argument parsing.
  3. **(checker round 3):** two bugs, one a severe self-inflicted regression from round 1's own fix — the script's OWN lock directory (created before the dirty-check ever ran) tripped its OWN "refuse if `$repo` is dirty" guard on every single default invocation, unless the caller happened to already `.gitignore` `.secondmate/`. And the ledger's path was never excluded from that same check either, so the script broke itself after its own FIRST successful use once `audit/merge-ledger.jsonl` existed as an untracked file. Fixed (round 4) by excluding the lock directory via a git pathspec — but that fix used BASENAME matching, which the very next checker round found was ALSO wrong (too broad: it excluded any path in the repo sharing that name, swallowing a genuinely dirty unrelated file), and STILL never excluded the ledger. Properly closed only in round 5, replacing basename matching with a new `_repo_relative_path` helper computing each artifact's EXACT path relative to `$repo`, using git's literal pathspec magic — discovering along the way that an out-of-repo absolute path passed as a literal pathspec fatally errors rather than harmlessly no-op-ing, requiring the exclusion argument to be omitted entirely rather than synthesized as a fallback string.
  4. **(checker round 3, same round, separate finding):** `PUSH_FAILED` had zero automated regression coverage despite the checker independently verifying the actual behavior was already correct via a manual rejecting `pre-receive` hook — added as a real selfcheck test using the same technique.
  5. **(checker round 4):** `--worktree` was only checked for existence and being SOME git working tree — never validated as an ACTUAL linked worktree of `--repo`. An independent, stale `git clone` of the same repository (frozen at an old `main` since it never fetched again) could pass verify-gate.sh's own freshness check against its OWN stale local refs (commit SHAs are portable across clones) while the real merge silently landed into `--repo`'s genuinely different, newer state — completely bypassing the "review is fresh relative to what actually gets merged" guarantee the entire script exists to provide. Fixed with a `git-common-dir` equality check between `--repo` and `--worktree`, resolved via `pwd -P` (physical path) specifically to avoid a real macOS false-positive the maker discovered mid-fix: `/tmp` is itself a symlink to `/private/tmp`, so a naive logical-path comparison would have mismatched a genuinely linked worktree against its own primary checkout.
  6. **(checker round 5):** any `git merge` failure was unconditionally classified as `MERGE_CONFLICT`, but git can refuse a merge for reasons that never even attempt a real three-way merge — most commonly a repo-configured `pre-merge-commit` policy hook (sign-off requirements, commit-message linting). Reproduced directly with a hook that unconditionally rejects: `git ls-files -u` showed zero unmerged paths, proving no real conflict occurred, yet the ledger recorded `MERGE_CONFLICT` — misleading the entire point of the closed-enum reason-code design (a human/dispatcher would reach for the wrong remediation). Fixed with a new `MERGE_REJECTED` code, distinguished via `git ls-files -u` captured BEFORE `git merge --abort` runs (since abort erases the evidence).
  7. **Checker round 6: clean pass, zero findings**, explicit "ship recommendation: ship" after being specifically asked to hunt for any OTHER instance of the same "two different failure causes folded into one reason code" pattern that round 5 had just found.
- **Supervisor verification discipline:** every fix above was independently reproduced by the supervisor with a from-scratch repro (real independent clones, real `pre-merge-commit`/`pre-receive` hooks, real concurrent invocations, real macOS `/tmp` symlink behavior confirmed directly) BEFORE being routed to the maker as confirmed, and every fix was independently re-verified plus mutation-tested before the next round. One mutation test (reverting round 4's fix to basename-only exclusion) reproduced BOTH round 3's findings simultaneously in one revert, confirming they shared the exact same root flaw.
- **Outcome:** verify-gate PASS at `4c24d3c` (checked-sha match, 7 real commits) → human hold answered `merge` (genuine per-task AskUserQuestion) → merged to main `--no-ff` at `35d1940` (three real conflicts — `plugin.json`, `README.md`, `docs/ARCHITECTURE.md` — against the already-merged `claim-ledger` branch, hand-resolved to keep both branches' additions; version bumped to `0.1.16`, one past main's already-merged `claim-ledger` bump, since merge-sequencer's own branch had independently reached `0.1.17` through its own extra rounds from the same base — a round-count artifact, not a merge-count one) → full repo-wide selfcheck chain re-run clean (`ALL_OK`) on the actual merged commit → `claude plugin validate .` passed → pushed → worktree/branch/pane torn down.
- **Lesson:** this task is the clearest demonstration yet that "found nothing new, clean pass" is only trustworthy when the checker is EXPLICITLY asked to hunt for the SAME underlying bug class recurring in a new place, not just re-confirm what's already fixed — round 6's clean pass came only after directly asking "is there another place where two different failure causes get folded into one ledger code," the exact pattern round 5 had just found. The other reusable lesson: the round-3→4→5 sequence on the dirty-check exclusion is a smaller-scale repeat of the "generalize, don't patch" pattern already seen in the sibling `fix-plan-committee-tool-call` task this session — basename matching was wrong from the start, not a reasonable first attempt that needed narrowing; the eventual exact-path fix was simpler AND more correct than the two patches that preceded it.
