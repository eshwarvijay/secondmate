- **Rounds:** an exceptionally long task — **15 checker rounds** (`global.openai.gpt-5.6-terra`, `qa/coverage`/`redteam/access-control`/`qa/test-reality` lenses), 14 of which found and fixed a real, independently-reproduced, confirmed defect; round 15 returned a clean pass with an explicit SHIP recommendation. In order (full detail in `decision.md`):
  1. A genuine SIGPIPE-under-`set -o pipefail` race in 3 selfcheck assertions (`git log --oneline | grep -q pattern`), the ORIGINAL symptom that motivated this task's continuation — root-caused via direct reproduction (a 500KB `git log` reliably triggered it), fixed by capturing to a variable first, then discovering even THAT wasn't fully safe for large payloads and finishing with bash-native `[[ =~ ]]`/`[[ == * ]]` matching (no subprocess, no pipe, size-independent).
  2. Hook rejections checked with priority only on RETRY failures, never the initial push — closed by checking hook-rejection signals first, always; an off-by-one attempt cap (4 real pushes instead of the documented 3); an inaccurate "--preflight-only has zero side effects" claim (its own `git fetch` updates a remote-tracking ref).
  3. A genuine concurrent server-side ref-transaction race ("cannot lock ref ... incorrect old value provided") ALSO carries the same "remote: "/"[remote rejected]" framing the hook check treated as absolute — fixed with a new, higher-priority ref-lock-race check; `--preflight-only` never validated `--branch` against `--checked-sha` (the same invariant the normal path already enforces) — fixed.
  4. The new ref-lock-race check's own free-text body matching ("cannot lock ref" anywhere) was fooled by a REAL, plausible hook message ("policy denied: cannot lock ref writes until CAB approval") — generalized to match ONLY git's own structural `(incorrect old value provided)` parenthetical; `--preflight-only`'s `merge-tree --write-tree` ALSO writes a dangling object to `$repo`'s object database, previously undocumented.
  5. The retry loop's own escalation check only escalated on a confirmed hook rejection — any OTHER failure (auth/network) fell through to "keep retrying" by default; fixed to fail closed (only continue when affirmatively still race-shaped).
  6. **The most severe finding of the task:** the retry loop released the singleton lock at the top of each attempt, before recovery's own fetch/merge/push — letting a SECOND, concurrent invocation targeting the SAME `--repo` mutate that same checkout WHILE the first was still mid-recovery, defeating the entire "serialize concurrent merges" purpose of this script. Reproduced directly with two real concurrent invocations (second completed in ~0s before the fix, ~3s — the first's full recovery sleep — after). Fixed by simply removing the premature release.
  7. A LOCAL `pre-push` hook (client-side, runs BEFORE git ever contacts the server) has NO "remote: " relay prefix at all, unlike a server-side hook — fooling both `_is_ref_lock_race` (a hook printing "(incorrect old value provided)" verbatim) AND the plain `_is_race` keyword fallback (a hook message containing an ordinary word like "behind") independently. Fixed with a filesystem-level check, `_repo_has_pre_push_hook`, disabling ALL text-based classification for any repo with one installed — documented as an accepted, honest trade-off.
  8. That new filesystem check itself had a TOCTOU: a pre-push hook that deletes itself as its own last action was gone from disk by the time anything checked for it afterward, silently hiding a policy rejection as a "successful" race recovery (rc=0). Fixed by sampling ONCE, before the first push, closing the window entirely.
  9. Docs (README/ARCHITECTURE) still said recovery "releases the lock," contradicting round 6's own fix; the supervisor's own round-9 accepted-limitation writeup ("a hook installed after the sample is an unavoidable residual") turned out to be based on a REASONING ERROR the checker correctly caught in round 10.
  10. **Round 10 corrected round 9's own error:** a hook installed sometime DURING the (potentially long) recovery fetch/merge, before attempt 2 or 3's own push, was still invisible to the single early sample — a materially larger window than the "sub-second instant" round 9 intended to accept. Fixed with monotonic OR-sampling (re-sample before every retry, only ever set true, never reset), closing the mid-recovery window without reopening round 8's fix.
  11. A stale roles-table doc line, plus two existing-but-uncovered code paths (`--preflight-only`'s own fetch failure, the recovery loop's own fetch failure) — both independently verified already-correct via direct mutation before adding regression tests for them.
  12. `--preflight-only --message ""` (or `--test ""`) silently bypassed the documented mutual-exclusivity refusal, since the check tested value emptiness rather than whether the flag was explicitly given.
  13. **`_is_race`'s ORIGINAL design (bare keyword match, unchanged since round 1) was vulnerable to ANY local stderr text**, not just pre-push hooks — reproduced with a fabricated, non-git message from a simulated transport helper (no installable hook file to guard against at all). Generalized the same structural fix already used for `_is_ref_lock_race`: require git's own bare `[rejected]` summary-line marker alongside the keyword.
  14. **A genuine PATH/supply-chain-level finding, categorically different from every prior round:** a PATH-precedence fake-`git` shim (or a custom transport/SSH/credential helper) can fabricate output matching EVERY structural marker this file relies on as unspoofable evidence. Unlike rounds 1-13 (all ordinary, legitimate git mechanisms), this requires tampering with PATH or the `git` binary itself. The supervisor used `AskUserQuestion` to get an explicit human decision rather than judging this alone — the human chose to accept it as a documented, out-of-scope limitation, citing `bin/caffeinate-guard.sh`'s own existing precedent for the identical threat class ("a PATH/supply-chain threat model outside this feature's scope"). No code change; documented in the header, README, and ARCHITECTURE.
