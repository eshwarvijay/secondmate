## 2026-09-04 — pi-scope-guard: pi extension confining pi maker sessions to their own worktree

- **Maker (pi/Qwen3-Coder-Next, medium thinking):** built `bin/scope-guard-extension.ts`, a pi `--extension` providing the same worktree-confinement and credential-command denial as the Claude-side `bin/scope-guard.py`, wired via explicit `--extension` flag into all pi-maker launch sites in `SKILL.md` (project-local auto-discovery mechanisms were investigated and confirmed non-functional, then removed as dead code). Required an unusually long tail of correction rounds spanning two sessions.
- **Checker findings resolved, most severe first (all real, all fixed in code):**
  1. **Return-shape mismatch silently blocking everything:** `_is_path_violation` returned `{valid,reason}` while the `tool_call` handler destructured `{allowed,reason}` — `allowed` was always `undefined`, so every Read/Write/Edit/NotebookEdit call was unconditionally denied regardless of actual scope. This is the most severe bug found in either scope-guard task (Claude or pi side) and survived multiple prior rounds because no round had tested a positive (in-scope) case — every previous probe only checked that an out-of-scope path was blocked, which looks identical to "everything is blocked" from the outside. Fixed by unifying both helpers' return shape to `{allowed,reason}`.
  2. **Fail-open on exception:** any exception thrown inside `decide()` caused pi's `tool_call` handler to allow the call rather than deny it — proven with a crashing trailing-pipe Bash command (`echo hello |`) reaching Bash unblocked. This is structurally the most concerning class of bug, since it means any *future* bug in the guard (known or unknown) silently disables confinement instead of blocking. Fixed with a fail-closed `try/catch` wrapper around `decide()`, matching the policy `scope-guard.py` already established in the earlier `scope-guard-hook` task.
  3. **Shared mutable regex state leak:** a module-level `RegExp` with the `/g` flag retained `lastIndex` across separate tool calls within the same pi session, so a blocked `python3 -c "...open('/etc/hosts')..."` call would succeed if retried a second time in the same session. Fixed by constructing a fresh `RegExp` per call.
  4. **`realpathSync` crash on nonexistent paths:** an earlier round's symlink-resolution fix used Node's strict `fs.realpathSync` (throws `ENOENT` on any missing path component) to match Python's lenient `os.path.realpath` (resolves through existing prefixes, passes nonexistent trailing segments through unresolved) — this would have crashed on virtually every ordinary Bash command and every new-file `Write`. Fixed with a `resolveSymlinks()` helper that walks the path resolving only existing components.
  5. **Shell-string interpolation fail-open:** `is_maker_worktree`'s `execSync` interpolated `cwd` into a shell command string; a worktree path containing a shell metacharacter (e.g. a literal `"`) broke the shell parse, the exception was swallowed, and the session was treated as "not a maker" (fail-open, upstream of the `decide()` fail-closed wrapper). Fixed by switching to `execFileSync`'s argv-array form, matching `scope-guard.py`'s existing `subprocess.run([...])` pattern — no shell involved.
  6. Smaller parity/coverage gaps: missing `--extension` on a second (headless) and later two more (on-fail retry) launch sites; unterminated-quote shell syntax not denied (vs. `scope-guard.py`'s `shlex` parity); non-functional `.pi/extensions/`/`settings.json` auto-discovery removed as dead code.
- **Supervisor verification discipline:** every fix in this task was independently re-verified by the supervisor via real executed probes against a live `pi --extension` process (including a debug-instrumented copy of the extension logging `decide()`'s actual return value) before being trusted — never accepted on the maker's own "DONE"/self-report. This directly caught that the maker left uncommitted changes on the working tree three separate times despite the standing "commit before DONE" checklist already present in its prompt.
- **Gates:** verify-gate PASS (`a002d15`, checked-sha match) → human hold answered `merge`, citing the user's standing advance authorization for this task batch (lessons-checklist, round-metrics-ledger, pi-scope-guard) rather than a fresh per-task approval → merged to main `--no-ff`.

- **Checker findings resolved, most severe first (all real, all independently reproduced and fixed across 10 checker rounds):**
  1. **State-machine reference-version bug (round 1):** stale-vs-silent_drift compared `running_version` against `marketplace_version` instead of `installed_version` against `marketplace_version` — a real, healable version bump could be misreported as unhealable "silent drift" whenever the running script's own version happened to coincide with the marketplace's.   2. **Weak heal verification (round 1):** only checked "did the SHA change at all," accepting any wrong SHA (e.g. from a corrupt or buggy `claude plugin update`) as a successful heal. Fixed to require the post-update SHA equal the actual fetched remote SHA.
  3. **Unreachable stale-lock recovery (round 1) → real demonstrated TOCTOU race (round 2):** the original stale-lock-steal code was structurally unreachable for the realistic "lock already existed when first checked" case. The fix for that was itself proven racy by the checker's own orchestrated probe (a delayed `rm -rf`, based on a stale staleness-decision, destroying a different process's already-replaced fresh lock) — closed for real with an atomic `mv`-based claim plus post-claim re-verification, not another narrowing re-check.
  4. **A failed heal silently reported as script success (round 2):** `heal()`'s own captured failure was never checked, and the script's unconditional final exit-code line was unrelated to heal outcome regardless. Fixed by capturing the real exit code in the `--heal` dispatch branch and calling `exit` on it directly, bypassing the always-overriding final line — plus a genuine bash gotcha found independently by both the supervisor (mutation testing) and the maker (own tracing) in the same round: `[ "$heal_failed" -eq 1 ] && return 1` as a function's last line returns the `[ ]` test's own exit status when false, inverting success into failure on every call regardless of `$heal_failed`'s actual value.
  5. **The same "optimistic reporting on unverifiable/hard-abort state" bug class, independently found 4 more times across rounds 3-6:** the report table showing `[ok]`/plain "STATUS: ready" for a genuinely `stale` row (only `MISSING` was ever counted toward the summary); the identical gap for a malformed/unparseable `installed_plugins.json` (`UNKNOWN` state); `heal()` never dispatching to `_heal_secondmate` at all for a `missing` marketplace checkout (the spec's required hard-abort silently never fired); and the same STATUS-line gap recurring a third time specifically for the missing-marketplace row. Each instance found by a different checker round reviewing a different code path; each fix mirrored the pattern already established for the earlier instances (a dedicated counter, wired into the STATUS line's precedence chain).
  6. **Two already-correct hard-abort paths with zero regression coverage (round 7):** `git fetch` failure and `claude plugin update` failure were both already handled correctly in production code (independently verified by the supervisor with real fixtures before authorizing any change) but had never been exercised by a dedicated test. Test-only additions, no production change.
