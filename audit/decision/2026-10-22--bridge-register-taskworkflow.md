## 2026-10-22 — submit-task subcommand design + scoped-down coverage ruling, checker-corroborated; 2 process gaps surfaced (claim/hold ledger cwd, stray git diff.external)

## Key decisions and findings

**Design: separate `submit-task` subcommand, not a `--task-file` flag on `submit`.** 4/6 plan-committee models favored bolting a flag onto the existing `submit`; adhd's independent ideation and qwen3-80b both argued for a new subcommand instead, on the grounds that it makes "zero behavior change to the existing `submit`/`worker` path" a structural, zero-diff-inside-`runSubmit` fact rather than a tested claim, and matches this CLI's own convention of three independent flat subcommands. Supervisor adjudicated in favor of the subcommand — reinforced by the fact that it was the only design actually compatible with the dispatcher's scope boundary (no edits to `internal/planrun/task.go`), which the plan committee wasn't told about and which ruled out several planners' assumed `LoadTaskFile`-in-`task.go` sketches.

**Round 1 checker finding — real bug, not a false positive.** `fs.Parse` in Go's `flag` package stops at the first non-flag argument, silently stuffing everything after it (including a later `--workflow-id`, deliberately never defined on this FlagSet) into `fs.Args()` without erroring. This meant the invariant "passing `--workflow-id` to `submit-task` must fail loudly" only held for a clean argument ordering, not every ordering. Fixed generically with a post-`Parse` `fs.NArg() > 0` check, closing the whole class (any stray trailing argument), not just this one flag name. Maker added a direct regression test reproducing the exact failing ordering.

**Round 2 checker finding — judged disproportionate, scoped down rather than fully implemented.** The qa/coverage lens asked for dedicated tests of `dial()` failure, `StartTask` duplicate-workflow-ID conflict, and waited-result (`run.Get`) timeout/error paths, plus a CLI-level idempotency regression test. Supervisor verified via `grep` that `dial()` is a single function shared verbatim by the new `runSubmitTask` and the pre-existing `runSubmit`/PlanWorkflow path, and that `runSubmit` itself has had zero dedicated tests of any kind in this repo, before or after this task. Ruled: holding only the new code to a stricter error-injection-coverage bar for an identical shared failure mode than the already-shipped code has ever had is an inconsistent new bar, not "matching existing convention" — and the task's actual stated requirement (prove a real submission reaches a real server and starts the right workflow type) was already met. Added only the cheap, high-value missing/malformed-task-file case; explicitly declined the rest with this reasoning carried into the checker's next-round context.

**Round 3 — the decline was independently corroborated, not just asserted.** Rather than taking the supervisor's ruling on faith, the checker went and probed each declined path live against a real dev server (bad `TEMPORAL_ADDRESS` for dial failure, a repeated submission for duplicate-start conflict, `--wait 1ns` for timeout) and confirmed all three already behave correctly. Verdict: pass, zero findings. This is the strongest form of validation available for a scoping judgment call — an adversarial reviewer actually went and checked, rather than the supervisor's reasoning going unverified.

## Escalations / process gaps surfaced

1. **Claim/hold ledger-location gap (recurring, second occurrence).** Both `claim-ledger.py claim` and `hold.py hold` for this task were run from the supervisor's ambient secondmate-repo cwd instead of the bridge repo, so both silently landed in secondmate's own ledger rather than bridge's. Caught by the human when checking the hold from the bridge repo's cwd and finding nothing. Same class of mistake `bridge-claim-step` hit earlier with `claim-ledger.py` specifically. Recorded in the flow entry as a named, recurring gap (not a one-off) — these ledger-resolving scripts infer their ledger root from the calling process's cwd with no cross-check against the task's actual target `--repo`, and nothing in the current SOP prose forces a `cd` before the first claim/hold call of a task. Worth a structural fix upstream (either an explicit `--repo`/ledger-root flag on these scripts, or an unmissable cd-first instruction in the SOP's Claim/Spawn step).

2. **Stray `.git/config` `diff.external` entry in the bridge repo (environmental, not caused by this task).** Points at a deleted temp script (`/var/folders/.../tmp.4EA1J7eLks/ext.sh`), breaking every plain `git diff` in that repo, including `launch-checker.sh`'s own internal diff auto-injection for every round of this task. Worked around (not fixed) by manually generating diffs with `--no-ext-diff` and feeding the checker via `--live-file`/`--repo`. Flagged for a human to clean up directly — editing `.git/config` is not this supervisor's call to make unilaterally.
