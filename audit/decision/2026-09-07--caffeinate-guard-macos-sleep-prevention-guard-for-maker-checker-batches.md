## 2026-09-07 — caffeinate-guard: macOS sleep-prevention guard for maker/checker batches

- **Maker (pi/Qwen3-Coder-Next, medium thinking):** built `bin/caffeinate-guard.sh`. First implemented a per-task-id mkdir-based lock (matching the original ask's literal wording about "concurrent tasks"), then — after the human redirected mid-task — rewrote it as a single session-scoped singleton guard once the supervisor and human jointly recognized the concurrency requirement was about tasks running in parallel underneath a single sequential supervisor caller, not about the guard's own start/stop commands being invoked concurrently with each other.
- **Design decision (human-directed, not the supervisor's own call):** offered three options via AskUserQuestion after 4 unconverging checker rounds on the per-task-id design (ship with the limitation documented / one more patch round / redesign the primitive) — human chose "redesign the primitive." Before that redesign was even implemented, the human independently proposed the simpler session-scoped architecture, which was adopted instead, discarding the in-flight primitive-redesign work.
- **Checker findings resolved, most severe first (all real, all fixed in the simplified design):**
  1. **Documentation-wiring bug:** `stop` was originally placed inside each task's own per-task Teardown step (step 9 of "The loop", which fires once per task) — under the new session-scoped design this would kill the shared guard the moment the *first* of several concurrently-running tasks finished, while siblings were still active. Fixed by moving `stop` out of the per-task loop entirely, replaced with an explicit instruction for the supervisor to call it once, directly, only after confirming every task/worktree in the batch is torn down.
  2. **Concurrent-start orphan leak:** genuinely parallel tasks each redundantly calling `start` at their own Spawn step (exactly this repo's own real usage pattern) could all pass the "is a guard already running" check before any wrote the pidfile, leaking untracked processes. Fixed with a short-lived atomic bash-noclobber claim wrapping just the check-then-spawn critical section — explicitly scoped narrower than the abandoned per-task-id lock (no owner-identity persistence, no stale-lock grace windows, since there's no per-task dimension left to track).
  3. **Command-substitution hang:** the backgrounded `caffeinate` process had no explicit stdout/stderr redirect, so it inherited the caller's own stdout pipe — `result=$(caffeinate-guard.sh start)` would hang for the full 8-hour TTL rather than returning once the parent script exited. Fixed with an explicit `>/dev/null 2>&1` redirect on the backgrounded process.
  4. **A discarded custom `--ttl` value:** a redundant variable redeclaration silently overwrote a validated, caller-supplied TTL with the hardcoded default right before the value was used to spawn the process.
  5. **A cluster of `set -e`/`pipefail` selfcheck bugs**, the largest time sink of the task: a legitimate zero-match `grep` (e.g. "no caffeinate running yet," a normal state) registering as a pipeline failure under `pipefail` and silently killing the whole selfcheck with zero diagnostic output; a bare command's exit code checked on a separate, unreachable line under `set -e`; and a genuinely environment-specific artifact — this development machine's shell has a custom `grep` function wrapping `ugrep`, whose spawned subprocess exposes the *unbracketed* search text in its own `ps aux` argv, defeating the standard `[c]affeinate` self-exclusion idiom used throughout the file for orphan-detection checks. Root-caused and fixed only after the supervisor independently reproduced each failure in isolation with `bash -x` tracing rather than trusting the maker's own (repeatedly incorrect) theories about the cause — including one moment where the maker's own reasoning was heading toward weakening `_stop`'s deliberate PID-recycling protection to "fix" a bug that was actually located in an unrelated test. The supervisor caught and blocked that specific misdiagnosis before any code changed.
  6. Two bugs specific to the now-abandoned per-task-id generation, fixed there before the design pivot: a stale-lock permanent deadlock (a crashed lock holder blocked every future `start` for that task-id forever — proven realistic since this exact session had already hit "retry the same command after a kill" scenarios) and a genuinely-alive-holder infinite hang (the lock's own 10-second timeout check was unreachable from the "holder is alive" branch of its retry loop).
- **Supervisor scope decisions (not bugs — deliberate accepted-limitation calls, none escalated this round since each closely matched precedent already set and endorsed earlier in this same task):**
  1. Two independent secondmate-orchestrating sessions on the same machine sharing this one host-wide singleton guard — out of scope; the feature protects one supervisor's one batch of work, not multiple concurrent supervisor sessions, and defending against that would mean reintroducing the exact per-caller concurrency machinery just removed.
  2. A `start`/`stop` overlap for the same guard requiring both a documented-contract violation and an artificially-held-open timing window (the checker's own repro used a wrapped `rm` to force it) to reach.
  3. The identity-fingerprint check assuming `caffeinate` in PATH is the real system utility, not an adversarially-substituted decoy — a PATH/supply-chain threat model outside this feature's stated purpose.
  All three are named explicitly in the script's own LIMITATIONS header comment.
