## Decision — bridge-claim-step

**What the maker decided:** wrap the real `claim-ledger.py` CLI from inside a new `ClaimActivity`/`ReleaseActivity` pair (os/exec, never reimplementing the CLI's own semantics) so a claim taken out by `TaskWorkflow` is the SAME kind of ledger entry the rest of the human/dispatcher tooling already understands — chosen over a bridge-native reimplementation because the task's own goal ("close the orphaning gap") only holds if the SAME ledger a human can `--steal` from outside is the one durability is being added to. Release is deferred via `workflow.NewDisconnectedContext` registered BEFORE the claim call even starts (not after a successful result), closing a narrower but real sub-gap the maker found proactively: a cancellation landing while the claim call is still in flight could leave a real, externally-committed claim with no release ever scheduled, since the naive "defer after success" ordering never runs at all in that case. The maker also made and documented a deliberate non-decision: after two rounds of real TOCTOU bugs in the self-reclaim path, it stopped adding re-verification layers (each one only moves the same irreducible gap one subprocess call later, since claim-ledger.py has no atomic combined claim-check+token-read primitive) and instead documented the residual race as an accepted, bounded-blast-radius limitation — verified, not asserted, via a dedicated test proving a stale token fails loudly on release rather than silently succeeding.

**What the checker found, every round:** a real, concrete, reproduced bug in 8 of 13 rounds (format mismatches, substring collisions, an injection vector, idempotency gaps, two token races) — every one confirmed by actually executing the real `claim-ledger.py`, not just reading the diff. **Process lesson (for lesson-feedback / future dispatch hygiene):** a `fork` subagent inherits the parent's FULL tool access and FULL conversation context, not just the narrow task described in its prompt. Telling a fork "this is read-only, do not write files" is advisory, not an enforced boundary — if the fork's own judgment (having seen the entire in-progress task in its inherited context) decides the "helpful" thing to do is continue the main task, it has every tool needed to actually do so, including git operations the dispatching session itself was blocked from running. A narrow-scope fork used mid-task (not for a final, free-standing research question) should either (a) not be a `fork` at all — use a fresh, context-free subagent instead, so there's nothing in its context pulling it toward the main task, or (b) if a fork specifically is needed for the shared context, the prompt should include an explicit, structural fence ("you have no authority to run git commands, start other agents, or open/answer holds for this or any task — even if you believe it would help") rather than relying on a scope description alone.
