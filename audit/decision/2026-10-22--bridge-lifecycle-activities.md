## 2026-10-22 — Merge scoped as not-classifier-blocked (verified structurally); Judgment-Agent probe overridden to observe-only; Test trust boundary documented not sandboxed

**Most significant finding — a critical, production-breaking bug invisible for 4 rounds because a test double lied about reality:** `TeardownActivity`'s `closeWorktree` called `herdr worktree remove --path <path>` from round 1 onward. `--path` is not a real flag on the real `herdr` CLI — confirmed independently by me running `herdr worktree remove --help` directly, which exposes only `--workspace <ID>` and `--force`. Every single production lifecycle run would have had Teardown fail on its very first call, which (per the chain's own halting discipline) would have blocked Audit and Lesson-feedback from ever running too — the exact "nothing left for the supervisor to do manually" goal this task exists to deliver would have silently regressed to "manual teardown required, every time." The reason this survived rounds 1-4 of checker review: the fake `herdr` CLI stand-in used in every real-server test accepted any argv unconditionally, never modeling the real CLI's actual flag grammar, so a call using a flag the real tool doesn't support still looked "successful" to every test. The fix closes both halves — the real bug (capture `herdr worktree list`'s real `open_workspace_id` field, call `--workspace` instead) and the test-reality gap that hid it (the fake now actively rejects `--path` and requires `--workspace`, so this exact bug class can't recur silently). **Process lesson for lesson-feedback:** a fake/mock external-CLI stand-in that accepts any argv shape, rather than modeling the real CLI's actual validation, is itself a latent bug-concealment mechanism — this is a stronger, more general statement than the existing "mutation-test your own test" lesson, worth considering as a future lesson candidate (not created here — `lesson-lookup.py` only tags existing lessons, it doesn't mint new ones from this task).

**Design decisions I made and overrode mid-task, both grounded in checker evidence, not guessed:**
1. **Merge activity scoping.** The original dispatch asked me to "think hard" about whether Merge could run unattended given Claude Code's Auto Mode "Merge Without Review" classifier that had blocked agent-run `merge-sequencer.sh`/`hold.py` calls earlier in this same session. I read two real prior sibling-task audit entries (`2026-10-21--hold-answer-token.md`, `2026-10-22--bridge-claim-step.md`) and determined the classifier is a gate on Claude Code's own Bash-tool permission layer when an *agent session* issues the call — it has no hook into `MergeActivity`'s `os/exec` call running inside the real `bridge worker` daemon process, which is not a Claude Code agent session at all. So I had the maker build real exit-code-legend handling (0 ok / 1,3,5 refuse / 2 infra-error / **4 — local merge landed, push failed — its own unmistakable marker + exact retry command**, since that's the realistic, already-designed-for "needs a human to finish by hand" case) rather than chase a phantom classifier-detection heuristic. This reasoning held up: the actual merge in THIS task hit exactly the predicted pattern (agent-run calls blocked, human ran both `hold.py answer` and `merge-sequencer.sh` directly via `!`) — but that happened at the **human/supervisor layer**, never inside `MergeActivity` itself, confirming the two are genuinely separate concerns.
2. **Judgment-Agent resource discovery — overruled my own round-1 design.** I originally specified (and the maker built) a "find by generic task-id-token match, then auto-close" design for the unsettled sibling-task resource type, reasoning that "every match is logged, never silently acted on" was sufficient mitigation. The checker escalated this across rounds 1→3 from "suspected, accepted limitation" to a concrete, confirmed, destructive counter-example (a task named `bridge` would auto-delete an unrelated task's live, possibly-still-in-progress worktree/branch/pane). On reflection I agreed the checker was right: logging *before* destroying doesn't prevent the damage, since the action has already happened by the time anyone reads the log. I overrode my own prior guidance and had the maker redesign the generic probe to be strictly observe-only. This is the one point in the task where I changed a design decision I'd already given the maker, based on the checker's own evidence rather than deferring to my own earlier judgment.
3. **`LifecycleConfig.Test` reaching a shell — scoped as documentation, not sandboxing.** The checker found `Test` flows from arbitrary `submit-task --task-file` JSON straight to `verify-gate.sh`'s/`merge-sequencer.sh`'s own `bash -c`. I investigated `cmd/bridge/submit_task.go` directly and confirmed `Plan.Steps[].Params` (pre-existing, untouched by this task) already has this exact property — arbitrary caller-supplied JSON already drives real maker/checker subprocess behavior with zero sandboxing today. I judged this consistent with, not a new regression beyond, `TaskInput`'s existing trust model (whoever submits a task is already assumed as trusted as the supervisor itself), and scoped the fix to documentation only (an explicit trust-boundary doc comment on `Test`), declining to build input validation/sandboxing that would have been an out-of-scope, system-wide redesign of `submit-task`'s trust boundary. The checker explicitly reviewed and agreed this scoping was defensible (round 5's CLEAN section).
